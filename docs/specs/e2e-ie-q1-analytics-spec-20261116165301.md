# Техническая спецификация стаб-сервиса очередей
**Маркер:** E2E IE Q1  
**Идентификатор:** E2E IE Q1 analytics spec 20261116165301  
**Тип:** Спецификация (spec)  
**Статус:** Черновик

## 1. Назначение и область применения
Стаб-сервис очередей — упрощённая in-memory реализация сервиса очередей сообщений, предназначенная для использования в средах разработки, интеграционного и E2E-тестирования (включая сценарии, помеченные `E2E IE Q1`). Сервис имитирует базовое поведение брокера очередей (создание очередей, публикация, получение, подтверждение/возврат сообщений) без гарантий долговечности и высокой доступности, присущих production-решениям.

## 2. Цели и нецели

### 2.1. Цели
- Предоставить детерминированный и предсказуемый интерфейс для тестов, зависящих от очередей.
- Обеспечить быстрое развёртывание без внешних зависимостей (БД, брокеры).
- Поддержать базовые операции жизненного цикла сообщения: enqueue, dequeue, ack, nack/requeue.
- Обеспечить наблюдаемость состояния очередей для отладки тестов.

### 2.2. Нецели
- Долговременное хранение данных и восстановление после перезапуска.
- Гарантии exactly-once, упорядочивание между разными очередями, партиционирование.
- Горизонтальное масштабирование, кластеризация и репликация.
- Полная совместимость с протоколами/семантикой конкретных брокеров (RabbitMQ, Kafka, SQS и т.д.), если это не оговорено отдельно.

## 3. Термины
- **Очередь (Queue)** — именованный FIFO-буфер сообщений.
- **Сообщение (Message)** — полезная нагрузка с метаданными и уникальным идентификатором.
- **Producer** — клиент, публикующий сообщения.
- **Consumer** — клиент, получающий и обрабатывающий сообщения.
- **Visibility timeout** — период, на который сообщение скрывается от других потребителей после выдачи до ack/nack/таймаута.
- **DLQ (Dead Letter Queue)** — опциональная очередь для сообщений, превысивших лимит попыток обработки.

## 4. Общее описание решения
- **Тип хранения:** in-memory (процессная память).
- **Модель доставки:** at-least-once (при использовании ack/nack и visibility timeout).
- **Порядок:** FIFO в рамках одной очереди (best-effort; при requeue порядок может нарушаться).
- **Изоляция:** состояние изолировано в пределах экземпляра сервиса; перезапуск очищает все данные.
- **Интерфейс:** HTTP/JSON API (основной); при необходимости допускается обёртка/адаптер под клиентский SDK тестового контура.

## 5. Функциональные требования

### 5.1. Управление очередями
- Создание очереди с параметрами (имя, visibility timeout, max receive count, DLQ).
- Получение метаданных очереди (глубина, количество сообщений в обработке, конфигурация).
- Удаление/очистка (purge) очереди.
- Получение списка очередей.

### 5.2. Публикация сообщений
- Публикация одного сообщения в указанную очередь.
- Поддержка произвольного строкового/JSON payload и опциональных атрибутов (headers/metadata).
- Присвоение уникального `messageId` и времени создания.
- (Опционально) пакетная публикация.

### 5.3. Получение и обработка сообщений
- Получение одного или нескольких сообщений (`maxMessages`, по умолчанию 1).
- Перевод выданных сообщений в состояние `in-flight` на время `visibilityTimeout`.
- Подтверждение успешной обработки (`ack`) по `messageId`/`receiptHandle`.
- Отрицательное подтверждение (`nack`) с опциями: вернуть в очередь немедленно / с задержкой / отправить в DLQ.
- Автоматический возврат сообщения в очередь по истечении `visibilityTimeout` с инкрементом счётчика попыток.

### 5.4. DLQ и повторные попытки
- При превышении `maxReceiveCount` сообщение перемещается в DLQ (если настроена) либо удаляется (если не настроена), с фиксацией причины.
- Возможность чтения сообщений из DLQ тем же API.

### 5.5. Наблюдаемость и управление тестовым состоянием
- Health/readiness endpoint.
- Endpoint статистики/инспекции очередей для assertions в тестах.
- Сброс всего состояния сервиса (`reset`) для изоляции тест-кейсов (доступен только в тестовом режиме).

## 6. Нефункциональные требования
- **Производительность (стаб):** достаточная для E2E/интеграционных тестов; целевой ориентир — сотни операций/сек на одном экземпляре (без жёстких SLA).
- **Задержка:** обработка in-memory операций — миллисекунды (p95 в пределах тестового окружения).
- **Надёжность:** отсутствие падений при некорректных входных данных; корректные коды ошибок.
- **Детерминизм:** предсказуемое поведение FIFO и visibility timeout для воспроизводимости тестов.
- **Безопасность:** отсутствие персистентного хранения секретов; доступ к административным операциям (`reset`, `purge`) ограничивается тестовым окружением/конфигурацией.
- **Ресурсы:** ограничение максимального размера очереди/сообщения для защиты от OOM в тестах.

## 7. API (предлагаемый контракт, HTTP/JSON)

Базовый префикс: `/api/v1`

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка состояния сервиса |
| `POST` | `/queues` | Создать очередь |
| `GET` | `/queues` | Список очередей |
| `GET` | `/queues/{queueName}` | Метаданные и статистика очереди |
| `DELETE` | `/queues/{queueName}` | Удалить очередь |
| `POST` | `/queues/{queueName}/purge` | Очистить очередь |
| `POST` | `/queues/{queueName}/messages` | Опубликовать сообщение |
| `POST` | `/queues/{queueName}/messages/receive` | Получить сообщения (dequeue/lease) |
| `POST` | `/queues/{queueName}/messages/{messageId}/ack` | Подтвердить обработку |
| `POST` | `/queues/{queueName}/messages/{messageId}/nack` | Вернуть/отклонить сообщение |
| `POST` | `/admin/reset` | Сброс всего состояния (тестовый режим) |

### 7.1. Примеры моделей данных

**Создание очереди (`POST /queues`)**
```json
{
  "name": "orders-events",
  "visibilityTimeoutMs": 30000,
  "maxReceiveCount": 5,
  "deadLetterQueueName": "orders-events-dlq"
}
```

**Публикация (`POST /queues/{queueName}/messages`)**
```json
{
  "payload": { "orderId": "123", "event": "created" },
  "attributes": { "source": "test", "traceId": "abc" },
  "delayMs": 0
}
```

**Ответ получения (`POST /queues/{queueName}/messages/receive`)**
```json
{
  "messages": [
    {
      "messageId": "msg-uuid",
      "receiptHandle": "lease-uuid",
      "payload": { "orderId": "123", "event": "created" },
      "attributes": { "source": "test" },
      "receiveCount": 1,
      "enqueuedAt": "2026-11-16T16:53:01Z"
    }
  ]
}
```

### 7.2. Коды ответов и ошибки
- `200/201` — успешное выполнение.
- `204` — успешное выполнение без тела (ack/purge/delete).
- `400` — некорректный запрос (валидация имени, параметров, payload).
- `404` — очередь или сообщение не найдено / lease недействителен.
- `409` — конфликт (очередь уже существует, повторный ack по устаревшему lease).
- `429/503` — превышение лимитов (размер очереди/памяти), при наличии ограничений.
- Формат ошибки: `{ "error": { "code": "STRING_CODE", "message": "..." } }`.

## 8. Модель состояний сообщения
1. `READY` — доступно для получения.
2. `IN_FLIGHT` — выдано потребителю, ожидает ack/nack или истечения visibility timeout.
3. `DEAD_LETTERED` — перемещено в DLQ.
4. `DELETED` — удалено после ack (терминальное).

Переходы:
- `READY -> IN_FLIGHT`: receive.
- `IN_FLIGHT -> DELETED`: ack с валидным `receiptHandle`.
- `IN_FLIGHT -> READY`: nack(requeue) или истечение visibility timeout (receiveCount++).
- `IN_FLIGHT/READY -> DEAD_LETTERED`: `receiveCount > maxReceiveCount` при наличии DLQ.

## 9. Конфигурация
| Параметр | По умолчанию | Описание |
|---|---|---|
| `HOST` / `PORT` | `0.0.0.0` / `8080` | Адрес и порт HTTP-сервера |
| `DEFAULT_VISIBILITY_TIMEOUT_MS` | `30000` | Таймаут видимости по умолчанию |
| `DEFAULT_MAX_RECEIVE_COUNT` | `5` | Лимит попыток до DLQ/удаления |
| `MAX_MESSAGE_SIZE_BYTES` | `262144` | Максимальный размер сообщения |
| `MAX_QUEUE_DEPTH` | `10000` | Максимум сообщений в очереди |
| `ENABLE_ADMIN_RESET` | `true` (test) | Разрешение endpoint `/admin/reset` |
| `LOG_LEVEL` | `info` | Уровень логирования |

## 10. Логирование и метрики
- **Логи (структурированные):** создание/удаление очередей, publish/receive/ack/nack, переходы в DLQ, ошибки валидации, административные операции.
- **Метрики (минимум):** `queue_depth`, `messages_in_flight`, `messages_published_total`, `messages_acked_total`, `messages_nacked_total`, `messages_dead_lettered_total`, `request_latency_ms`.

## 11. Ограничения и допущения
- Данные хранятся только в памяти и теряются при перезапуске.
- Отсутствуют гарантии доставки при аварийном завершении процесса.
- Конкурентный доступ обеспечивается в пределах одного процесса (механизм синхронизации определяется реализацией).
- Спецификация задаёт контракт стаба для тестового контура; конкретный стек реализации, формат развёртывания и интеграция с существующим тестовым фреймворком подлежат уточнению при внедрении.

## 12. Критерии приёмки (предлагаемые)
- Сервис поднимается локально/в CI и отвечает на `GET /health`.
- Поддерживаются операции создания очереди, публикации, получения, ack и nack в соответствии с контрактом API.
- Сообщение, не подтверждённое в пределах `visibilityTimeout`, становится доступным повторно с увеличенным `receiveCount`.
- При превышении `maxReceiveCount` сообщение попадает в DLQ (если настроена).
- `POST /admin/reset` очищает состояние между тестами (при включённом флаге).
- Сценарии E2E, помеченные `E2E IE Q1`, могут использовать сервис как замену внешней очереди без изменения проверяемой бизнес-логики (в рамках поддерживаемого контракта).
